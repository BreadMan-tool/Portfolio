Case Study / Unity Live Game Client

빠지냥

코어 게임만 있던 프로젝트를 넘겨받아 2025년 8월부터 2026년 6월까지 Lucky Pass 제작, 게임플레이 기믹 추가, 리더보드, 경쟁 콘텐츠, 분석 이벤트, IAP/광고/SDK, Crashlytics 기반 안정성 관리, 리소스 최적화와 라이브 QA를 담당했습니다.

Period 2025.08 - 2026.06
Role Unity Client Developer
Focus Live Ops / UI / SDK
Evidence 1,547 local commits

Overview

기존 라이브 게임을 인수해 기능을 확장하고 운영 가능한 구조로 정리했습니다.

빠지냥은 코어 게임플레이만 있던 Unity 모바일 게임이었고, 제가 이 프로젝트에서 처음 맡은 큰 작업이 Lucky Pass 제작이었습니다. 이후 시즌패스 운영, 게임플레이 기믹, 리더보드, 경쟁 콘텐츠, 구매/광고, 외부 SDK, 분석 이벤트, 크래시 안정성 관리까지 라이브 게임으로 확장하는 작업을 이어서 담당했습니다.

초기에는 코드베이스를 익히며 빠르게 기능을 출시하는 데 집중했고, 콘텐츠가 늘어난 뒤에는 반복 작업을 줄이는 방향으로 구조를 정리했습니다. 보상 테이블과 시즌 리소스 분리, 스테이지 기믹 모델/에디터 대응, 클라우드 세이브, 콘텐츠 스케줄러, SDK 라우팅, Crashlytics 기반 라이브 QA, 리소스 최적화 도구가 핵심입니다.

2026.03 - 2026.05

Analytics-Ready Event Architecture

Firebase, ThinkingData, Singular, GameAnalytics 이벤트를 기능 코드에 흩뿌리지 않고 공통 라우터에서 관리했습니다. 기능 코드는 콘텐츠 상태 변화만 명확히 호출하고, SDK별 발사 대상은 `TrackNetwork` 플래그로 선택합니다.

  • `EventDef`로 이벤트명 상수화
  • `EventManager.Track`으로 Firebase, ThinkingData, Singular, GameAnalytics 라우팅
  • Firebase custom dimension 호환을 위해 파라미터 string 정규화
  • GameAnalytics wrapper 제약에 맞춘 단일 파라미터 전송 처리

Crash Stability / Live QA

Firebase Crashlytics로 비정상 종료가 발생하지 않은 사용자 비율을 확인하며 라이브 빌드를 운영했습니다. 2026년 4월 1일부터 5월 21일까지의 확인 구간에서는 대부분 95% 이상을 유지했고, 특정 빌드에서 하락한 구간도 원인 추적과 후속 빌드 수정으로 회복했습니다.

  • Crash-free users 지표를 기준으로 빌드별 안정성 변화를 확인
  • 하락 구간 발생 시 Crashlytics 이슈, 재현 조건, 최근 변경사항을 함께 추적
  • 불명확한 크래시는 여러 빌드에 걸쳐 로그와 재현 경로를 보강하며 수정
  • 기간, 기준 지표, 하락 구간, 후속 빌드 대응 방식까지 함께 기록

Feature Evolution

기존 기능을 운영 가능한 구조로 발전시켰습니다.

빠지냥 작업의 강점은 신규 기능 추가뿐 아니라, 한 번 만든 기능을 라이브 운영 중 반복 수정하면서 데이터 구조, UI 성능, 리소스 교체, 이벤트 추적까지 계속 개선한 점입니다.

Leaderboard

Prefs, Manager, UI item/podium 구조로 시작해 주간 랭킹, 월드/국가 랭킹, 가상 유저 시뮬레이션, 스크롤 최적화, Endless League 메달 랭킹까지 확장했습니다. 이후 닉네임 중복, 캐시, 프리팹 구조를 정리하며 라이브 운영에 맞게 안정화했습니다.

Design Tradeoff

장점은 서버 없이도 빠르게 경쟁감을 만들고, 오프라인 경과와 주간 리셋을 클라이언트에서 안정적으로 처리할 수 있다는 점입니다. 단점은 진짜 글로벌 경쟁 검증에는 한계가 있어, 서버 랭킹이 아닌 클라이언트형 라이브 콘텐츠라는 범위를 명확히 두고 설계했습니다.

Season Pass

Lucky Pass 제작 후 시즌별 운영이 반복되면서 보상 테이블 override, Addressables 기반 리소스 그룹, 정보 페이지, Spine 연출로 확장했습니다. 새 시즌 추가 시 코드 수정보다 데이터/리소스 교체 중심으로 대응할 수 있게 만들었습니다.

Competition

기존 경쟁 콘텐츠를 Streak Race, UFO/Air Balloon, WorldCup, Smelt Festival처럼 변형 가능한 구조로 확장했습니다. 상태, 타이머, 실패/재도전, 보상, UI 연출, 이벤트 발사를 같은 운영 흐름으로 맞췄습니다.

Store / Package

기간형 상품과 반복 노출 상품이 늘어나면서 PackageManager에서 노출 기간, 인터벌 판매, 구매 상태, 남은 시간 문구, IAP 조건을 한 곳에서 판단하도록 정리했습니다.

Resource Workflow

반복적인 리소스 점검을 Unity Editor 도구로 옮겼습니다. 텍스처, 아틀라스, Addressables, Spine, 중복/미사용 리소스를 탭 단위로 확인해 라이브 빌드 전 정리 비용을 낮췄습니다.

Development Growth

빠른 기능 출시에서 운영 가능한 구조와 제작 방식으로 확장했습니다.

Ramp-Up

처음에는 기존 코드에 익숙해지는 시간이 필요했기 때문에, Lucky Pass와 기믹 작업을 만들며 런타임 모델, UI 패널, Prefs, 리소스, StageEditor 흐름을 빠르게 따라갔습니다. 이후 같은 패턴이 반복되는 지점을 찾아 테이블, SO, 매니저, Editor 도구로 정리했습니다.

Content Scale

콘텐츠가 늘어나면서 하나씩 직접 관리하는 방식의 한계가 생겼습니다. 그래서 콘텐츠 스케줄러, 공통 타이머, 컨셉 key, 보상/상태 흐름을 만들고, 라이브 콘텐츠가 같은 기준으로 열리고 닫히도록 정리했습니다.

Presentation Polish

콘텐츠 연출이 아쉽다는 피드백을 받은 뒤에는 단순 기능 완료에서 멈추지 않고, 보상 등장, 매칭, 정산, 진행 단계, 아이템 이동, 팝업 전환이 더 명확하게 보이도록 DOTween과 UI 상태 전환을 다듬었습니다.

AI-Assisted Workflow

전담 멘토가 없는 1인 개발 환경에서 AI를 기술 검토 파트너처럼 사용했습니다. 영어 SDK 문서 해석, 외부 SDK 연동 순서 정리, 버그 발생 지점 가설화, UI 연출 구현 아이디어를 먼저 검토한 뒤 실제 코드베이스 컨벤션에 맞춰 적용했습니다.

Stability Metric

Crash-free users를 기준으로 라이브 빌드 안정성을 관리했습니다.

2026년 4월 1일 - 5월 21일 확인 구간에서 빠지냥은 대부분 95% 이상의 crash-free users를 유지했습니다. 후반부 하락 구간은 인수인계와 빌드 변경이 겹친 시점에 발생했으며, 이후 원인 추적과 수정 빌드로 회복했습니다.

운영 기준

단일 크래시 수치보다 버전별 추세, 신규 이슈 발생 시점, 최근 변경사항과의 연결을 우선 확인했습니다. 안정성은 항상 95% 이상을 목표로 보고, 하락 시 다음 빌드에서 회복시키는 것을 기준으로 삼았습니다.

대응 방식

Crashlytics 이슈, 재현 가능성, 디바이스/OS 분포, 직전 기능 변경을 함께 확인했습니다. 바로 원인이 드러나지 않는 문제는 로그와 방어 코드를 추가한 빌드를 반복하며 재현 범위를 줄였습니다.
