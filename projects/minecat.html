Case Study / Unity Client from Scratch

깡깡냥

프로젝트 생성부터 클라이언트 구조, 게임플레이, UI/HUD, 데이터 테이블, 상점/IAP, 무기 VFX까지 직접 구축했습니다. 빠지냥에서 반복적으로 만들었던 라이브 기능 경험을 Breadmore Core 기반 프로젝트 구조로 옮긴 개인 주도 개발 케이스입니다.

Period Project Start - Present
Role Sole Unity Client Developer
Focus Core / Gameplay / UI
Foundation Breadmore Core

Overview

라이브 게임에서 배운 기능들을 새 프로젝트의 기본 구조로 재구성했습니다.

깡깡냥은 기존 코드를 인수한 프로젝트가 아니라, 프로젝트 생성부터 직접 만든 Unity 모바일 게임입니다. 빠지냥에서 시즌패스, 상점, 보상, UI, SDK, 안정성 대응을 만들며 반복했던 패턴을 Breadmore Core 기반 부트스트랩, 저장, 리소스, IAP, UI 구조 위에 다시 설계했습니다.

초반부터 폴더링, MVC 형태의 모델/뷰 분리, UI_ 네이밍, CSV 데이터 로딩, 오브젝트 풀, 투사체 시스템, HUD 모듈, 상점과 구매 흐름을 같은 기준으로 정리했습니다. 빠른 프로토타입보다 이후 기능이 늘어도 같은 방식으로 확장되는 클라이언트 기반을 만드는 데 집중했습니다.

Key Work

대표 작업

01

Project Start

Project Bootstrap / Breadmore Core Integration

빈 Unity 프로젝트에서 시작해 Breadmore Core 패키지를 적용하고, 게임 시작에 필요한 부트 순서와 공통 시스템을 구성했습니다. 저장, 씬 전환, 플랫폼, 리소스, IAP 같은 기반 기능은 패키지 위에 얹고 깡깡냥 전용 부트 단계와 매니저를 붙였습니다.

  • Breadmore Core, Save, Scenes, Resource, IAP, UI, Localization, Analytics, Ads 패키지 의존성 구성
  • `BootStep` 기반으로 저장, 게임 데이터, 첫 씬 진입, IAP 초기화 순서 정리
  • `Main`, CoreManager, ContentManager로 프로젝트 전역 진입점과 콘텐츠 매니저 구조 구성
02

Core Architecture

MVC Gameplay Structure

광물, 플레이어, 동료, 펫을 단일 MonoBehaviour 로직에 두지 않고 Model과 View로 나눴습니다. 게임 상태와 표시 오브젝트의 책임을 분리해 밸런스 계산, 타겟 판정, Spine 표시, 풀링 반환을 각 레이어에서 처리할 수 있게 만들었습니다.

  • `MineralModel`, `PlayerModel`, `CompanionModel`로 런타임 상태와 계산 로직 분리
  • `MineralView`, `PlayerView`, `CompanionView`, `PetView`로 표시와 풀링 생명주기 처리
  • `DefenseField`, `MineShaft`, `MapModule`에서 모델, 뷰, 스테이지 진행을 연결
03

Gameplay Systems

Projectile System / Spatial Target Grid

무기 공격과 연출을 위해 투사체 예약, 활성 투사체 Tick, 강제 정리, 충돌 판정을 담당하는 시스템을 만들었습니다. 많은 광물을 대상으로 하는 범위/라인 판정은 공간 그리드로 후보를 줄여 반복 계산 비용을 낮췄습니다.

  • `ProjectileSystem`에서 delayed fire, active list, scheduled list, scene 하위 정리 처리
  • `SpatialTargetGrid`로 원형 범위, 라인 범위 타겟 조회 구성
  • Projectile, impact VFX, weapon type별 spark/smoke material을 연결해 공격 피드백 구현
04

Performance / Tools

Object Pooling / Prefab Validation

광물, 펫, 투사체, UI 아이템처럼 반복 생성되는 오브젝트를 풀링하도록 만들었습니다. 프리팹에 필요한 컴포넌트가 없을 때 즉시 에러를 내고 반환하도록 처리해, 런타임에서 조용히 깨지는 문제를 줄였습니다.

  • `InGameObjectPool`에서 key 기반 spawn, prewarm, release, budget, stats 제공
  • `InGamePoolItem`과 `IPooledObject`로 spawn/despawn 생명주기 통일
  • Editor setup 도구로 인게임 프리팹과 UI 프리팹 연결 상태를 반복 확인
05

UI / HUD

Generated UI Panels / Modular HUD

HUD와 패널을 처음부터 `UI_` 네이밍과 공통 베이스에 맞춰 만들었습니다. 무기, 펫, 도감, 환생, 상점, 보상 팝업, 오프라인 보상 팝업을 같은 패턴으로 열고 닫을 수 있게 구성하고, HUD는 기능별 파트로 쪼개 갱신 범위를 줄였습니다.

  • `MineCatPanel`, `MineCatPopup` 기반으로 패널/팝업 동작 기준 통일
  • `HudCurrencyController`, `HudStageBarController`, `HudUpgradeButtons`, `HudPopupButtons` 등 HUD 파트 분리
  • 무기/펫/컬렉션/도감/상점/환생 패널과 보상, 오프라인, 모달 팝업 구현
06

Data / Live Ops Foundation

CSV Data / Rewards / Shop / IAP

무기, 펫, 스테이지, 보상, 상점 구성을 코드에 고정하지 않고 데이터와 서비스로 분리했습니다. Breadmore IAP와 Unity Purchasing을 연결해 에디터 더미 구매와 실제 구매 provider를 나누고, 구매 완료, 실패, entitlement 상태를 상점 갱신 흐름에 연결했습니다.

  • `Weapon.csv`, `Pet.csv`, `Stage.csv`와 row class, `GameDataBootStep`으로 로컬 데이터 로딩
  • `RewardDatabase`, `RewardTable`, `RewardData`로 보상 정의와 지급 흐름 구성
  • `BreadmorePurchaseService`, `UnityPurchasingIAPProvider`, `IAPBootStep`으로 구매 흐름 구성

Breadmore Core

빠지냥에서 반복되던 구현을 공통 패키지 구조로 발전시켰습니다.

빠지냥에서는 Firebase, GameAnalytics, Singular, Remote Config, IAP, 로딩, 저장 흐름을 기능별 코드와 매니저에서 직접 연결했습니다. 라이브 운영에는 맞았지만, 새 프로젝트마다 같은 패턴을 다시 만들고 SDK별 예외 처리를 반복해야 했습니다.

Breadmore Core는 이 경험을 바탕으로 만든 UPM 패키지 모음입니다. 게임 코드는 static facade만 호출하고, 실제 SDK와 저장소는 provider로 교체할 수 있게 분리했습니다. 깡깡냥에서는 이 구조를 프로젝트 시작부터 적용해 부트, 저장, 리소스, IAP, UI, Analytics, Ads를 같은 규칙으로 연결했습니다.

빠지냥

SDK, 이벤트, Remote Config, 로딩, 구매 흐름이 라이브 기능마다 직접 연결되었습니다. 출시 속도는 빠르지만 SDK 교체, 테스트 provider, 초기화 순서 관리가 기능 코드에 묻기 쉬웠습니다.

깡깡냥 + Breadmore Core

`BootStep`, `Save`, `IAP`, `Analytics`, `Scenes`, `Resource`, `UI` 같은 facade를 먼저 두고, 실제 구현은 provider와 게임별 adapter로 연결했습니다. 기능 코드는 SDK보다 게임 상태에 집중합니다.

Ordered Boot Steps

게임별 초기화 순서를 클래스 단위로 분리하고, 로딩 UI가 진행도를 구독할 수 있게 만든 구조입니다.

[BootStep(15)]
public class GameDataBootStep : BootStep
{
    public override Task RunAsync()
    {
        GameData.Load(new LocalGameDataSource());
        return Task.CompletedTask;
    }
}

await Boot.RunAsync();

Observable Save Data

빠지냥에서 PlayerPrefs/기능별 저장으로 흩어지던 값을 typed document와 observable field로 모았습니다.

public sealed class PlayerData : SaveData
{
    public SaveValue<long> Gold = new();
    public SaveDictionary<string, int> OwnedProducts = new();
    public SaveList<string> OwnedWeapons = new();
}

Save.Get<PlayerData>().Gold.Value += amount;
Save.SaveAll();

Provider-Based IAP

에디터에서는 Dummy provider, 실제 빌드에서는 Unity Purchasing provider를 연결해 같은 Store 코드로 처리합니다.

#if UNITY_EDITOR || MINECAT_DUMMY_IAP
IAP.SetProvider(DummyIAPProvider.Create(Store.IapProducts()));
#else
IAP.SetProvider(UnityPurchasingIAPProvider.Create(Store.IapProducts()));
#endif

Store.SetService(new BreadmorePurchaseService());
IAP.Initialize();

Feature Evolution

빠지냥에서 만들던 기능을 깡깡냥의 기본 시스템으로 발전시켰습니다.

Live Feature Experience

빠지냥에서 시즌패스, 보상, 상점, 광고, SDK 이벤트, 라이브 QA를 다뤘던 경험을 깡깡냥에서는 프로젝트 시작 단계부터 Breadmore Core의 부트, 저장, 구매, 분석, UI 구조에 반영했습니다.

Reusable Foundation

기능 코드가 Firebase, IAP, 로딩 UI를 직접 붙잡는 대신 facade와 provider를 통과하게 만들었습니다. 같은 게임 로직으로 dummy provider, Unity Purchasing, SDK adapter를 교체할 수 있습니다.

Data-Driven Content

무기, 펫, 스테이지, 보상, 상점이 코드 수정 없이 테이블과 ScriptableObject 흐름으로 확장될 수 있도록 데이터 로딩과 UI 갱신 구조를 먼저 만들었습니다.

Tradeoff

초반 구현 속도만 보면 구조화 작업이 많은 편이지만, 이후 무기 타입, 상점 상품, 보상 팝업, 신규 HUD 파트를 같은 패턴으로 추가할 수 있는 기반을 확보했습니다.

Workflow

새 프로젝트에서 모르는 영역을 빠르게 학습하며 구조와 연출을 검증했습니다.

ScriptableObject Structure

깡깡냥은 직접 만드는 프로젝트라 초반 구조 선택이 중요했습니다. 무기, 펫, 스테이지, 보상, 상점 구성을 코드에 고정하지 않기 위해 SO와 CSV를 어떻게 나눌지 검토하고, 데이터 변경이 UI와 게임플레이에 자연스럽게 반영되는 방향으로 정리했습니다.

Projectile Presentation

총탄과 무기 연출은 공격 타입, 이동 방식, impact, spark/smoke material이 함께 맞아야 했습니다. ProjectileSystem, ProjectileVfx, weapon material 구성을 만들면서 모르는 표현 방식은 AI와 먼저 검토하고, 실제 Unity 코드와 프리팹 구조에 맞게 적용했습니다.

Learning While Building

AI는 구현을 대신 맡기는 도구보다, 잘 모르는 구조를 빠르게 이해하고 선택지를 좁히는 학습 보조로 사용했습니다. SO 설계, 투사체 처리, VFX 구성처럼 익숙하지 않은 부분을 질문하고 비교하면서 작업 속도를 올렸습니다.

Validation Loop

제안받은 구조를 그대로 붙이기보다, 깡깡냥의 Breadmore Core 기반 부트/저장/리소스 흐름에 맞는지 확인했습니다. 기능 단위로 작은 구현을 붙이고, UI/HUD와 데이터 로딩까지 연결되는지 검증하며 확장했습니다.

What This Shows

Unity 클라이언트 개발자로서 보여주는 역량

기존 프로젝트를 인수하는 것뿐 아니라, 빈 프로젝트에서 서비스 가능한 클라이언트 구조를 직접 세울 수 있습니다.

라이브 게임에서 반복되는 저장, 보상, 상점, UI, IAP, 리소스 흐름을 공통 기반 위에 재사용 가능한 방식으로 구성할 수 있습니다.

게임플레이 성능과 유지보수를 위해 모델/뷰 분리, 풀링, 공간 그리드, 데이터 테이블을 함께 설계할 수 있습니다.
